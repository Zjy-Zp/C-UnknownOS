## 8.2 模块职责与依赖方向

| 模块 | 职责（一句话） | 依赖（只允许向下） |
|---|---|---|
| `vmm.c` | 对外的唯一门面：初始化、创建/销毁 VM、汇总统计 | svm / vmcb / npt / vcpu / vdev |
| `svm.c` | 与 AMD 硬件打交道的最小层：探测、使能、指令封装 | 无（只用 `common.h`） |
| `vmcb.c` | VMCB 生命周期与字段读写（含偏移断言） | svm |
| `npt.c` | 第二级翻译 | `paging.c`（页分配）+ 控制池 |
| `vcpu.c` | vCPU 状态机与 `VMRUN` 主循环 | vmcb / npt / vmexit |
| `vmexit.c` | 退出分发 + 五大退出码实现 | vdev（**唯一允许反向调用设备的地方**） |
| `vdev_*.c` | 纯设备状态机：`read(port)/write(port)`、`mmio_fault()`、`inject()` | 无（只写自己的寄存器堆） |

**依赖方向的关键约束**：`vdev_*.c` 不能反过来调用 `vcpu.c`。设备需要"向上"通知（比如 PIT 到期要注入中断）时，只能设置自己的 `pending_irq` 标志，由 `vmexit.c` 在主循环的固定检查点读取。这条约束把"设备模型的死循环/递归"从可能性里排除掉。

## 8.4 宿主执行体模型：没有内核线程时怎么办

cunos 的调度是**协作式、只在 `int 0x80` 里切换**，没有内核线程、没有抢占。因此 vCPU 不能"自己跑起来"，只能被调用者驱动。三种形态：

| 形态 | 阶段 | 做法 | 优点 | 缺点 |
|---|---|---|---|---|
| **同步阻塞**（推荐起步） | 1–2 | `vm_run()` 在 shell 上下文里进入 `while (1) { VMRUN; dispatch; if (guest_exit) break; }` | 零改动，30 行就能跑 | shell 被占住；guest 不退出时宿主无法响应键盘（中断本来也没开，影响有限） |
| **协作让出** | 3 | 每 N 次退出调用 `proc_yield()`（沿用 `int 0x80` 的切换路径） | 能同时跑其它 cunos 进程 | 让出点不确定，guest 时间片抖动 |
| **真内核线程** | 3.5 | 给 `proc_t` 加"内核态进程"类型，vCPU 作为独立执行体，栈 8KB | 最干净，未来可多 vCPU | 需要改 `proc.c` 的创建/切换/退出路径，约 200 行改动 |

阶段 1-2 的退出条件必须显式设计，否则 shell 永远回不来。本文规定 **guest 只能通过以下三种方式结束**：

1. 执行 `hlt` 且 `vcpu->exit_on_hlt = 1`（阶段 1 的 hello guest 用完就 hlt）；
2. 执行 `vmmcall`，超调用号为 `VMM_HC_EXIT`（阶段 2 起的正规退出通道）；
3. 三落 `SHUTDOWN`（异常路径）。

对应代码：

```c
int vm_run(vm_t *vm)
{
    vcpu_t *vc = vm->vcpu;
    for (;;) {
        vcpu_enter_guest(vc);                 /* VMRUN */
        int r = vmexit_dispatch(vc);          /* 处理最近一次退出 */
        if (r == VCPU_EXIT_NORMAL || r == VCPU_EXIT_SHUTDOWN)
            return r;
        if (r < 0)
            return r;                         /* 不可恢复错误 */
        vmm_stats.exits++;
    }
}
```

## 8.5 两个窗口、两个池：选址的完整推导

VMM 需要两类内存，且都要"宿主可随机访问、4KB 对齐、物理连续"：

| 池 | 物理范围 | 大小 | 用途 | 虚拟窗口 |
|---|---|---|---|---|
| **控制池** | `0x03000000 – 0x03FFFFFF` | 16MB | VMCB、HSAVE 页、NPT 各级表、IOPM(12KB)、MSRPM(12KB) | `0xDFC00000` 起 16MB |
| **guest RAM 池** | `0x04000000` 起，至多 128MB | ≤128MB | guest 的"物理内存" | `0xE0000000` 起 128MB |

**为什么是这两个地址？** 推导过程如下（这是本章最值得记住的部分）：

1. `paging.c` 里 `g_pmm_limit` 的计算是 `max(kernel_end+8MB, 32MB)`，再被硬钳到 `0x03000000`。也就是说 **`pmm` 永远不会分配 `≥0x03000000` 的页**。
2. `pmm` 分配出去的页会被 `paging_map_page()` 用于用户进程映射，从而**拆掉对应 4MB 块的大页**。被拆之后，该块内"物理地址 == 虚拟地址"这条性质对**未被显式映射的兄弟页**仍然成立（`paging_map_page` 会把 1023 个兄弟页填成恒等 `0x003`），但一旦某个虚拟地址被用户页覆盖（例如 `vaddr == paddr` 的巧合），恒等性就破。
3. 因此**不能依赖恒等映射**访问 VMM 的关键结构。要保证"任意时刻都能正确访问"，唯一稳的办法是**专用窗口 + 专用池**，窗口只由 VMM 建、只由 VMM 用。
4. 池必须放在 `pmm` 够不到的地方：`≥0x03000000`。
5. 窗口本身要占用虚拟地址空间。cunos 的 4GB 恒等映射里，`0x40000000`（`USER_MMAP_BASE`）、`0xC0000000`（`USER_STACK_TOP`）、`0x08048000`/`0x09000000`（`USER_ELF/BRK`）已被用户空间占掉，因此选 `0xDFC00000` 与 `0xE0000000` 这两个"宿主自己也不映射"的区域最安全。

映射代码（`vmm.c`）：

```c
#define VMM_CTL_PA_BASE  0x03000000u
#define VMM_CTL_SIZE     0x01000000u
#define VMM_CTL_VA_BASE  0xDFC00000u

#define VMM_RAM_PA_BASE  0x04000000u
#define VMM_RAM_MAX      0x08000000u
#define VMM_RAM_VA_BASE  0xE0000000u

static u32 g_ctl_off;      /* 控制池 bump 偏移 */
static u32 g_ram_size;     /* 实际 guest RAM 大小（= multiboot mem_upper 裁剪后） */

static int vmm_map_window(u32 va, u32 pa, u32 size)
{
    /* 硬规则：窗口区禁止 4MB MMIO 覆盖 */
    if (va >= 0xDFC00000u && va < 0xE8000000u) {
        /* 这里只是记录，真正的保护靠 paging_map_mmio_4m 的调用点自查 */
    }
    for (u32 off = 0; off < size; off += PAGE_SIZE) {
        if (paging_map_page(va + off, pa + off, 0x003) < 0) {   /* P|RW，非用户 */
            serial_puts("VMM: window map failed at 0x");
            serial_hex(va + off);
            serial_putc('\n');
            return -1;
        }
    }
    return 0;
}

u32 vmm_ctl_alloc_page(void)
{
    if (g_ctl_off + PAGE_SIZE > VMM_CTL_SIZE) return 0;
    u32 pa = VMM_CTL_PA_BASE + g_ctl_off;
    g_ctl_off += PAGE_SIZE;
    memset(ctl_va(pa), 0, PAGE_SIZE);
    return pa;
}

static inline void *ctl_va(u32 pa) { return (void *)(VMM_CTL_VA_BASE + (pa - VMM_CTL_PA_BASE)); }
static inline void *ram_va(u32 gpa) { return (void *)(VMM_RAM_VA_BASE + gpa); }
```

窗口映射的**成本**必须提前说清：128MB 窗口要建 32 张 4KB 页表（`paging_map_page` 每次拆一个 4MB 块就 `pmm_alloc_page()` 一页），并执行 32768 次 `invlpg`。在 QEMU/真机上这都是**几十毫秒级**的一次性开销，可以接受；但它会从 `pmm` 消耗 32 页，在 8MB 的 `pmm` 预算里占 0.16%，忽略不计。
