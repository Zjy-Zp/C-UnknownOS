# 第 16 章 Debian i386 的现实约束

## 16.1 内核 flavour 与 PAE

Debian 的 i386 端口近年明显收窄。要点：

- 老的 `686`（非 PAE）内核在较新版本中已不再提供，主流是 `686-pae`；
- `686-pae` 要求 CPU **支持 PAE**（`CPUID 0x00000001.EDX[6]`），并且内核会用 **PAE 分页**（`CR4.PAE=1`，页表是三级 8 字节表项）；
- **guest 的 PAE 与宿主无关**：guest 的 CR3 指向 GPA，经 NPT 翻译。所以"32 位非 PAE 的 cunos 宿主"完全可以跑 PAE guest——只要我们正确模拟 PAE 的页表寄存器语义（CR3 的 PDP 基址、`CR4.PAE`、`EFER.NXE`）。

**【需核对：目标 Debian 版本的内核 flavour、最低 CPU 要求、是否仍提供非 PAE 内核】** 这一条必须查发行版文档确认，不能按经验假定。

对应到代码：`ex_cpuid` 的 `0x80000001.EDX[6]`（PAE）必须按 guest 能力开关返回，且 `vm->cpu_pae_ok` 在阶段 3 置 1。如果我们的 CPUID 说不支持 PAE 而 Debian 只有 `686-pae` 内核，结果是内核启动早期打印一行 "This kernel requires the following features not present on the CPU: pae" 然后 `hlt`——这是个**很好**的失败模式（有明确输出），也说明 CPUID 虚拟化已经通了。

## 16.2 initrd 是绕不过去的

Debian 的 `initrd.img` 是"早期用户空间"，里面有加载 rootfs 所需的全部驱动。阶段 3 的引导必须：

1. 把 initrd 放进 guest RAM（`ramdisk_image` / `ramdisk_size`）；
2. 内核会把它解成 `tmpfs` 并执行 `/init`；
3. `/init` 需要**块设备驱动**才能找到 rootfs。

因此**"块设备驱动"是 Debian 启动的第二个硬门槛**（第一个是 PAE）：

| 方案 | initrd 里需要什么 | 我们的工作量 |
|---|---|---|
| ATA 模拟 + 内核自带 `ata_piix` | **不需要改 initrd**（`ata_piix` 在内核里，或已在 initrd 中） | 实现 ATA PIO 控制器 |
| virtio-blk | 必须把 `virtio_pci.ko` + `virtio_blk.ko` **注入 initrd** | 实现 virtio-blk + 改 initrd |

改 initrd 的方法（在 PC 上做，不属于 cunos 代码）：解压 `initrd.img`（cpio + gzip/zstd），把 `.ko` 放进 `kernel/drivers/`，重新打包。**这一步需要外部工具，属于"构建链"而非"内核功能"**，必须在文档里明确交代，避免"以为改代码就能解决"。

于是阶段 3 的推荐组合是：**ATA 模拟 + 不改 initrd**。等阶段 4 再叠 virtio 提升性能。

## 16.3 rootfs 复用 ext2 镜像

cunos 的 `ext2.c` 是**只读**的。这带来一个漂亮的机会：

- **guest 的 rootfs 就是一个 ext2 镜像文件**，放在宿主 ext2 分区上；
- 我们读它、把它当作"虚拟硬盘"给 guest（ATA 或 virtio 后端都是"按 LBA 读 512 字节"）；
- guest 自己带 ext2 驱动（Debian 内核内置），完全不需要我们用 `ext2.c` 去解析内容。

`ext2.c` 在 VMM 里的角色因此变成**"镜像文件读取器"**：给定镜像的 inode，按偏移读字节块，映射到 LBA。这正是 `vfs.c` 的 `read(fd, buf, n)` 能提供的。

写盘怎么办？三种策略：

| 策略 | 实现 | 适用 |
|---|---|---|
| **只读 rootfs** | 忽略所有写，返回成功（骗过 guest） | 阶段 3 验证启动，够用 |
| **内存 COW overlay** | 记录被写的 LBA + 新数据到一块 RAM，读时先查 overlay | 阶段 4，写不落盘（重启即还原） |
| **直写镜像** | 直接改 ext2 文件（需要 ext2 写支持） | 阶段 5，需要给 `ext2.c` 加写能力 |

**只读 + 假写成功**是最省事且最安全的（不会破坏宿主的 ext2 镜像）。风险是 guest 的 fsck 或日志重放会报错——用内核参数 `ro` 启动可以避开大部分。

## 16.4 内存预算：128MB 够不够

一次实算（这是"必须算而不是猜"的典型）：

| 项 | 大小 | 说明 |
|---|---|---|
| 内核镜像（解压后） | ~30MB | i386 内核 text+data，含模块化前的基础驱动 |
| initrd（解压后 tmpfs） | ~40MB | Debian initrd 压缩后 ~15MB，解开 40MB 左右 |
| 早期用户空间运行 | ~20MB | `/init` 脚本 + busybox |
| 挂载 rootfs 后 | 剩余 | 128 − 90 = 38MB 可用 |

结论：**128MB 只能"到 shell 为止"，装不下正常的使用**。且 `debian` 的最小 rootfs（debootstrap `minbase`）约 150–250MB 磁盘占用，内存里还要 page cache。

因此建议：

- 阶段 3 验证：`ram_size = 128MB`（足够到 shell）；
- 阶段 4 使用：`ram_size = 256MB` 或 `512MB`。

RAM 上限放宽到 256MB 后要复核三处：

1. **NPT 表页数**：256MB / 2MB = 128 个 2MB 页 → 1 PML4 + 1 PDP + 1 PD（一个 PD 有 512 项，128 项足够）→ 仅 3 页，可忽略。
2. **RAM 窗口页表**：256MB / 4MB = 64 个 4MB 块 → 64 张页表 + 65536 次 `invlpg` → 一次性开销约 50–100ms，可接受。
3. **物理内存是否够**：宿主需要 `0x04000000 + 256MB = 0x14000000`（320MB）以上的物理内存，且这块区域**不能被 `pmm` 碰**。`pmm` 硬上限是 `0x03000000`，所以安全。但如果真机只有 512MB 内存，320MB 给 guest 之后宿主只剩不到 200MB——**必须把 `vm_create` 的 `ram_size` 与 `multiboot` 报告的 `mem_upper` 做交叉校验**（第 10 章已列此检查）。

## 16.5 内核命令行：最小可用集

直引导 loader 传的 `cmdline` 直接决定"能不能起来"。推荐的分阶段配置：

```
# 阶段 3 最小集（最保守）
console=ttyS0,115200 earlyprintk=serial,ttyS0,115200 nokaslr ro root=/dev/sda1 rw=0

# 阶段 4 提速
console=ttyS0,115200 root=/dev/vda1 rootfstype=ext2 ro quiet

# 排障用（逐步加）
acpi=off noapic nolapic nosmp maxcpus=1
```

要点：

- **`console=ttyS0` 是生命线**：所有内核日志走我们的 UART，直接出现在宿主串口上。没有它，Debian 起来之后我们什么都看不到。
- **`earlyprintk=serial`** 让内核在 `console` 初始化之前就开始输出——调试早期启动（PAE 检查、e820 解析）必须靠它。
- **`acpi=off noapic nolapic`** 用于阶段 3（我们还没实现 ACPI 表与 LAPIC/IOAPIC）。加了这些参数，内核会退回 PIC 模式，正好匹配我们的 8259A 模型。
- **`nokaslr`**：即使 32 位内核不做 KASLR，某些版本仍会因为随机化偏移导致 `boot_params` 的假设失效，加上更稳。
- **`nosmp maxcpus=1`**：我们只有一个 vCPU，避免内核尝试启动 AP 而卡在 `INIT-SIPI`。

## 16.6 三个"必然遇到"的失败点

| 症状（串口输出） | 病因 | 对策 |
|---|---|---|
| `This kernel requires the following features not present on the CPU: pae` | CPUID 未报 PAE | `cpu_pae_ok = 1`，重测 |
| `Kernel panic - not syncing: No working init found` | initrd 未正确加载，或 `/dev/sda1` 不存在 | 检查 `ramdisk_image/size`；检查 ATA 控制器是否被识别（串口会打印 `ata1: ...`） |
| 无任何输出，`exit_code` 停在 `0x400` 反复退出 | 内核在 32 位入口前就因为 `boot_params` 非法而崩（如 `e820_entries=0`） | 打印 `boot_params` 的 `e820_entries` 与前三项 |
| 输出停在 `Freeing unused kernel memory` 之后 | 已经进入用户态，卡在 `/init`（多半是 rootfs 设备不存在） | 前面加 `debug`；检查块设备 |
| 输出停在 `Calibrating delay loop...` | PIT tick 不来（我们没注入 IRQ0） | 检查 `pit_tick` 与 `pic_raise` |
