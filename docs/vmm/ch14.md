# 第 14 章 客户机物理地址空间布局

## 14.1 布局表

32 位 guest 的物理地址空间必须"像一个 2005 年的 PC"，否则老内核的探测代码会四处碰壁。

| GPA 范围 | 大小 | 内容 | NPT 映射方式 |
|---|---|---|---|
| `0x00000000`–`0x0009FBFF` | 639KB | 常规内存（低端） | 2MB 大页（覆盖 `0`–`0x200000`） |
| `0x0009FC00`–`0x0009FFFF` | 1KB | EBDA（扩展 BIOS 数据区） | 同上（在大页内，内容是 RAM） |
| `0x000A0000`–`0x000BFFFF` | 128KB | VGA 显存（文本 0xB8000 + 图形 0xA0000） | **不映射** → NPF 交给 `vdev_vga` |
| `0x000C0000`–`0x000C7FFF` | 32KB | VGA BIOS（可选，放一段"`retf`"桩） | 映射到 guest RAM 的副本 |
| `0x000C8000`–`0x000FFFFF` | 224KB | 其它 ROM 区 | 映射（内容全 0xFF，符合"空 ROM"惯例） |
| `0x00100000`–`ram_top` | 至多 127MB | 扩展内存 | 2MB 大页批量铺 |
| `ram_top`–`0xEFFFFFFF` | 空洞 | 未实现 | **不映射** → NPF 报"访问未映射 GPA" |
| `0xF0000000`–`0xF07FFFFF` | ≤8MB | VBE 线性帧缓冲 | 首次 NPF 时逐 4KB 直通到影子缓冲 |
| `0xFEC00000`–`0xFEC003FF` | 1KB | IOAPIC（阶段 4 可选） | 不映射 → `vdev_ioapic` |
| `0xFEE00000`–`0xFEE003FF` | 1KB | 本地 APIC | 不映射 → `vdev_lapic`（阶段 4） |
| `0xFEE01000`–`0xFEFFFFFF` | — | 保留（AVIC/APIC 扩展） | 不映射 |
| `0xFFF00000`–`0xFFFFFFFF` | 1MB | BIOS ROM / 复位向量（SeaBIOS 路线才需要） | 映射到 guest RAM 的副本 |

## 14.2 布局的三条设计约束

**约束一：RAM 必须从 0 开始且连续。** 因为低端 639KB 的传统内存布局是所有 PC 软件的硬假设（`0x7C00` 引导、`0x500` BIOS 数据区、`0x9FC00` EBDA）。把 RAM 挪到 `0x10000000` 之类的"避开 MMIO"位置，会让 guest 的早期探测代码算出错误的可用内存。

**约束二：MMIO 必须放在"RAM 之上足够远"的地方。** 32 位 guest 没有"高地址 MMIO"（>4GB）可用，所以 MMIO 只能挤在 RAM 上方。我们把 RAM 上限钉在 128MB（`0x08000000`），把 MMIO 放在 `0xF0000000` 之上——中间留了 3.6GB 的空洞。这个空洞不是浪费：它让"guest 访问未映射地址"变成一个**明确的 NPF 错误**，而不是"悄悄读到 RAM 的某个位置"。

**约束三：EBDA 与 VGA 显存之间不能有"RAM 缝隙"。** `0x9FC00`–`0xA0000` 是 EBDA，紧邻 VGA。这块必须在 NPT 里是大页的一部分（即真的可读写 RAM），否则 guest 写 EBDA 会 NPF。

## 14.3 给 guest 的 E820 内存图

guest 内核靠 `int 0x15, eax=0xE820` 或 `0xE801` 得知内存布局。我们的 VMMCALL/BIOS 桩必须返回与 NPT **完全一致**的图，否则 guest 会去碰不存在的内存：

```c
typedef struct { u64 base; u64 len; u32 type; u32 acpi; } e820_entry_t;

static u32 build_e820(vm_t *vm, e820_entry_t *out)
{
    u32 n = 0;
    out[n].base = 0;                       out[n].len = 0x9FC00;  out[n].type = 1; n++;  /* 可用 */
    out[n].base = 0x9FC00;                 out[n].len = 0x400;    out[n].type = 2; n++;  /* 保留 */
    out[n].base = 0xA0000;                 out[n].len = 0x20000;  out[n].type = 2; n++;  /* VGA */
    out[n].base = 0xC0000;                 out[n].len = 0x40000;  out[n].type = 2; n++;  /* ROM */
    out[n].base = 0x100000;                out[n].len = vm->ram_size - 0x100000; out[n].type = 1; n++;
    out[n].base = VBE_GPA_BASE;            out[n].len = vbe_fb_size(vm);         out[n].type = 2; n++;
    return n;
}
```

**一致性检查工具**（强烈建议实现）：写一个 `vm_gpa_selftest()`，遍历 `build_e820()` 的每一项，对每个 2MB 步长调用 `npt_walk(gpa)`，断言"E820 说可用的地方 NPT 有映射、说保留的地方 NPT 无映射"。这个自检只要 30 行，能提前抓住"E820 与 NPT 打架"导致的 Debian 启动早期 `#PF` 死循环。
