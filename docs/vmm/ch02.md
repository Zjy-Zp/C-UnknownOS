# 第 2 章 Type-1 与 Type-2：cunos 的 VMM 到底算哪一类

## 2.1 三条判据

教科书的"Type-1 裸金属 / Type-2 宿主型"二分法经常在具体产品上失效（KVM 既像 Type-1 又跑在 Linux 里）。工程上更好用的是下面三条可判定的判据：

| 判据 | 问题 | 判定含义 |
|---|---|---|
| J1 特权归属 | 谁在物理 CPU 的最高特权级（ring 0 / VMX-root / host mode）上拥有"最终调度权"？ | 有独立 hypervisor 内核 → Type-1；由通用 OS 内核兼任 → "内核内建型"（KVM 与 cunos 都属此） |
| J2 vCPU 调度者 | 谁决定"下一个时间片跑哪个 vCPU"？ | 由 hypervisor 自己的调度器决定 → Type-1；由宿主 OS 的进程调度器决定（vCPU 是一个普通线程）→ 宿主型 |
| J3 设备模型位置 | 设备模拟代码运行在哪个地址空间？ | 在 hypervisor 内 → Type-1；在用户态进程（QEMU/VirtualBox 前端）→ Type-2 |

## 2.2 逐个打分

| 系统 | J1 特权归属 | J2 vCPU 调度 | J3 设备模型 | 归类 |
|---|---|---|---|---|
| VMware ESXi | ESXi 自有内核（VMkernel） | VMkernel 调度器 | VMkernel 内 | 纯 Type-1 |
| Xen（PV/HVM） | Xen hypervisor 独占 ring 0，Domain0 在 ring 1/3 | Xen 调度器 | Domain0 里的 QEMU | Type-1 |
| KVM | Linux 内核在 ring 0，用 SVM/VMX 扩展 | Linux CFS 调度 vCPU 线程 | 用户态 QEMU（或 vhost 内核加速） | Type-1 变体（内核内建）+ 用户态设备 |
| VirtualBox / VMware Workstation | 宿主 OS 在 ring 0，hypervisor 借驱动加载 | 宿主 OS | 用户态 VBox 进程 | Type-2 |
| WSL2 | Hyper-V（Type-1）之上跑轻量 Linux VM | Hyper-V 调度 | 宿主侧 `vmwp` + 9P 文件服务 | Type-2 的用户体验 / Type-1 的实现 |
| **cunos VMM** | **cunos 内核在 ring 0，自身调用 VMRUN** | **cunos 的 `proc.c`（阶段 3 起）** | **cunos 内核内的 `vdev_*.c`（阶段 2 起）** | **Type-1 变体（内核内建、单 VM 优先）** |

**结论**：cunos 的 VMM 在 J1 与 J3 上完全满足 Type-1（hypervisor 与设备模型都在 ring 0 的同一个内核里），在 J2 上暂时退化——因为 cunos 现在**没有内核线程、没有抢占**，vCPU 只能作为一个"同步阻塞调用"被 shell 驱动（详见 8.4）。所以准确的表述是：

> cunos VMM = **Type-1 形态的内建式 hypervisor**：具备裸金属式的特权与设备归属，但 vCPU 调度在阶段 1–2 由调用方（shell）隐式驱动，阶段 3 之后才升级为 cunos 自己的调度实体。

这个定位有一个直接好处：**不需要用户态组件**。没有 QEMU 那样的独立进程，也没有 socket 式的 VMM↔设备通道，一次 IO 退出的处理就是一次函数调用（`vdev_uart_out()`），延迟在数百纳秒量级而不是数十微秒。代价是：任何设备模型的 bug 直接是内核 bug，因此第 13 章会把设备模型写成"纯状态机 + 无动态内存"的形式。

## 2.3 与 KVM / WSL2 / virtio 的关系

三个名字经常被混为一谈，实际上分属三个不同的抽象层：

- **KVM**：Linux 内核里的一个子系统，把 SVM/VMX 包装成 `/dev/kvm` 接口。它证明了"OS 内核兼任 hypervisor"这条路可行，本文在架构取舍上参考其分层思想（VMCB 管理 / 退出处理 / 设备模型三层分离），但**不引用其任何代码**，且 cunos 的约束更硬：没有 `mmap`、没有信号、没有 `ioctl`、没有 per-CPU 变量、没有 RCU。
- **WSL2**：一个产品形态，本质是 Hyper-V（Type-1）上的一台轻量 Linux VM，加上跨 VM 的文件与进程互操作服务。它与 cunos 的关系是"反例"：WSL2 之所以能那么快落地，是因为微软已经有 Hyper-V 和完整的 Linux；cunos 两者都没有，所以只能自己写 VMM。
- **virtio**：一套**设备接口规范**（描述符环 + 通知机制 + 特性位），与 Type-1/Type-2 分类完全正交。它的价值在于"guest 侧驱动是标准的"——Debian 内核自带 `virtio_blk`/`virtio_net` 驱动，只要 cunos 侧实现 device 端，就能省掉一整套 ATA 控制器模拟。这是阶段 4 的关键杠杆（见 13.6）。

## 2.4 栈位置对照

```
 ┌──────────────────────────── cunos 方案 ────────────────────────────┐
 │  ring 3  │  cunos 用户程序（shell / 编辑器 / pie）                  │
 │  ring 0  │  cunos 内核                                            │
 │          │   ├── 既有：paging / mm / proc / vfs / ext2 / pci / vga │
 │          │   └── 新增：vmm/ （svm.c vmcb.c npt.c vcpu.c vmexit.c   │
 │          │            vdev_pic/pit/uart/pci/blk/vbe.c）             │
 │  SVM     │  VMRUN ↓ / #VMEXIT ↑                                   │
 │  guest   │  Debian i386：内核态(ring0) + 用户态(ring3)              │
 └────────────────────────────────────────────────────────────────────┘

 ┌──────────────────────── KVM 方案（对照，不引用代码）───────────────┐
 │ 用户态 │ QEMU（设备模型 + 机器模型）  ← ioctl/socket →            │
 │ 内核态 │ Linux（mm/sched/KVM）                                    │
 │ SVM    │ VMRUN ↓ / #VMEXIT ↑                                     │
 │ guest  │ 任意 OS                                                  │
 └────────────────────────────────────────────────────────────────────┘
```

差别一目了然：KVM 把设备模型放在用户态以获得故障隔离，cunos 把设备模型放在内核态以获得零拷贝与低延迟。这个选择的代价在第 20 章的风险表里以"R3 设备模型内存越界"的形式出现。
