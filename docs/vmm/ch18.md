# 第 18 章 调试与验证体系

## 18.1 日志分级与格式

```c
#define VMM_LOG_ERR   0
#define VMM_LOG_WARN  1
#define VMM_LOG_INFO  2
#define VMM_LOG_TRACE 3   /* 每次退出都打 */

extern int g_vmm_log_level;

#define VLOG(lvl, fmt, ...) do { \
    if ((lvl) <= g_vmm_log_level) { \
        serial_puts("[VMM] "); serial_puts(fmt); serial_putc('\n'); \
    } } while (0)
```

**统一前缀 `[VMM]`**，与 guest 的输出区分（guest 走 UART 的数据寄存器，我们走"直写宿主串口"，虽然物理上是同一个串口，但前缀能把两者分开）。建议在 guest 输出前加 `[G]` 前缀（由 `vdev_uart` 自动加会干扰 guest 看到的内容，所以**不加**，靠"host 的在前面、guest 的在后面"的时序区分）。

## 18.2 #VMEXIT 环形追踪

```c
#define TRACE_SIZE 256

typedef struct {
    u32 code;
    u32 rip;
    u64 info1;
    u64 tsc;
} exit_trace_t;

static exit_trace_t g_trace[TRACE_SIZE];
static u32 g_trace_head;      /* 下一个写入位置 */
static u32 g_trace_total;

void vmexit_trace_push(u32 code, u32 rip)
{
    exit_trace_t *t = &g_trace[g_trace_head & (TRACE_SIZE - 1)];
    t->code = code;
    t->rip  = rip;
    t->info1 = 0;              /* 需要时再读，避免每次都读 VMCB */
    t->tsc  = rdtsc();
    g_trace_head++;
    g_trace_total++;
}

/* shell: vm trace [n] —— 打印最近 n 条 */
void vm_trace_dump(int n)
{
    if (n > TRACE_SIZE) n = TRACE_SIZE;
    serial_puts("--- last exits (oldest first) ---\n");
    for (u32 i = g_trace_head - n; i < g_trace_head; i++) {
        exit_trace_t *t = &g_trace[i & (TRACE_SIZE - 1)];
        serial_hex(t->code); serial_putc(' ');
        serial_hex(t->rip);  serial_putc(' ');
        serial_dec64(t->tsc);
        serial_putc('\n');
    }
}
```

**这个环形缓冲是整个项目的"黑匣子"。** 当 Debian 卡死时，最后 256 条退出序列通常直接指出问题：连续同一 `RIP` 的 `IOIO` 说明轮询死循环（等了永远不会成立的状态位）；`RIP` 反复跳跃在 `0xFFFFxxxx` 说明 guest 在跑 BIOS 残桩；大量 `0x400` 说明缺页处理有 bug。

## 18.3 退出码统计

```c
static u32 g_code_hist[512];   /* 只统计低 9 位（0x000-0x1FF），0x400 类单列 */

void vmexit_stat(u32 code)
{
    if (code >= 0x400) g_npf_count++;
    else g_code_hist[code & 0x1FF]++;
}

void vm_stat_print(void)
{
    static const struct { u32 c; const char *n; } names[] = {
        {0x06A,"CPUID"},{0x070,"HLT"},{0x073,"IOIO"},{0x074,"MSR"},
        {0x077,"SHUTDOWN"},{0x079,"VMMCALL"},{0x07B,"PAUSE"},{0x07C,"INVLPGA"},
    };
    serial_puts("exit_code   name        count\n");
    for (u32 i = 0; i < sizeof(names)/sizeof(names[0]); i++) {
        serial_hex(names[i].c); serial_puts("  "); serial_puts(names[i].n);
        serial_puts("  "); serial_dec(names[i].c ? g_code_hist[names[i].c & 0x1FF] : 0);
        serial_putc('\n');
    }
    serial_puts("NPF(0x400 class) = "); serial_dec(g_npf_count); serial_putc('\n');
}
```

**这个统计表的最大价值是"数量级判断"**：guest 启动一次，如果 `IOIO` 是几万次而 `NPF` 只有几十次，说明设备模型在大规模轮询（正常）；如果 `IOIO` 是几百万次，说明 guest 卡在某个轮询循环里（异常）。**用数量级而不是绝对数判断，比"看某一条"有效得多。**

## 18.4 VMCB dump

```c
void vmcb_dump(u8 *vmcb)
{
    serial_puts("=== VMCB control area ===\n");
    dump32(vmcb, "ICR_READ",     0x000);
    dump32(vmcb, "ICR_WRITE",    0x002);
    dump64(vmcb, "INTERCEPT",    0x00C);
    dump64(vmcb, "IOPM_PA",      0x040);
    dump64(vmcb, "MSRPM_PA",     0x048);
    dump64(vmcb, "ASID",         0x058);
    dump64(vmcb, "EXIT_CODE",    0x070);
    dump64(vmcb, "EXIT_INFO1",   0x078);
    dump64(vmcb, "EXIT_INFO2",   0x080);
    dump64(vmcb, "NCR3",         0x0A8);
    serial_puts("=== state save area (selected) ===\n");
    dump64(vmcb, "ES.selector",  0x400);
    dump64(vmcb, "CS.base",      0x410);
    dump64(vmcb, "CS.limit",     0x418);
    dump64(vmcb, "CS.attrib",    0x420);
    dump64(vmcb, "RIP",          0x510);
    dump64(vmcb, "RSP",          0x520);
    dump64(vmcb, "RAX",          0x530);
    dump64(vmcb, "CR0",          0x4F0);
    dump64(vmcb, "CR3",          0x4E8);
    dump64(vmcb, "CR4",          0x4E0);
    dump64(vmcb, "EFER",         0x4D0);
    dump64(vmcb, "RFLAGS",       0x508);
}
```

**注意**：上面 `ES/CS` 的三元组偏移（selector/base/limit/attrib 的先后）与 9.5 表必须保持一致。段描述符在 VMCB 里的排列顺序与"段选择子、属性、限长、基址"的书写顺序**不一定相同**，【需核对：APM 中 segment 结构的字段顺序】。写 dump 函数时要按结构体而非"想当然的三元组"来读。

## 18.5 guest 内存与寄存器检查工具

```c
/* shell: vm peek <gpa> [len] */
void vm_peek(vm_t *vm, u32 gpa, u32 len)
{
    if (!gpa_range_ok(vm, gpa, len)) { serial_puts("out of range\n"); return; }
    u8 *p = (u8 *)ram_va(gpa);
    for (u32 i = 0; i < len; i++) {
        if ((i % 16) == 0) { serial_puts("\n"); serial_hex(gpa + i); serial_puts(": "); }
        serial_hex8(p[i]); serial_putc(' ');
    }
    serial_putc('\n');
}
```

配合 12.7 的超调用 `0x04`，还能让 guest 主动把某段内存吐给宿主——当 guest 内核有 `printk` 但串口不可用时，这是唯一的取数通道。

## 18.6 两条验证路径：QEMU 无头 vs 真机 U 盘

**先给结论：SVM 只能在真机上验证。** 原因必须讲清楚，否则会浪费大量时间在错误的路上：

| 环境 | 能否跑我们的 VMM | 原因 |
|---|---|---|
| **cunos 跑在裸金属上**（U 盘启动） | **能**（唯一可行） | 我们直接占用 SVM 硬件 |
| cunos 跑在 QEMU 的 TCG 模式 | 不能 | TCG 只做指令翻译，不实现 SVM 的 VMCB 语义，`CPUID 0x80000001.ECX[2]` 为 0，`EFER.SVME` 写不进去 |
| cunos 跑在 QEMU/KVM（L1）里再跑 SVM（L2） | 不能 | 需要 **嵌套虚拟化**（`nested=1`，仅 AMD 主机且 L0 是 KVM 时可能）；TCG 下完全没有。而且即使开了，`VMRUN` 的语义会退化为"L1 的 VMRUN 被 L0 拦截再模拟"，性能与行为都不可预期 |
| cunos 跑在 Hyper-V / VMware 虚拟机 | 不能 | 默认不向 guest 暴露 SVM（`CPUID 0x80000001.ECX[2]=0`、`VM_CR` 被锁）。这就是"本机 Hyper-V 屏蔽 SVM/NPT 字段"的直接后果 |

因此**验证路径只有一条**：把 cunos 做成可启动 U 盘，在物理 AMD 机器上启动。QEMU 仍然有用，但用途仅限于：

1. **宿主侧代码的编译与逻辑验证**（把 `vmexit_dispatch` 等纯逻辑函数用 mock VMCB 跑单元测试）；
2. **阶段 0/1 的"NPT 层级实验"在 QEMU 里做不了**——同样因为没有 SVM；
3. **作为对照组**：在 QEMU 的命令行里记录"KVM 的 SVM 有多快"，用来判断我们自己慢多少。

## 18.7 三落（Triple Fault）的定位方法

guest 内的异常链：一次异常 → 需要 IDT → IDT 无效（limit=0）→ `#GP`/`#DF` → 双故障 → 再失败 → `SHUTDOWN`。表现为**宿主立刻重启**，什么输出都没有。

定位手段（按代价从低到高）：

1. **打开 `intercept_exceptions` 的 `#GP`/`#PF`/`#DF` 位**，让 guest 的异常先在宿主侧被拦截并打印（`exit_code = 0x00D`）。这是最快的手段——三落之前一定会先有几个异常。
2. **在 VMCB 里预置一个"兜底 IDT"**：我们自己造 256 项 IDT，每项指向 guest 内存里的一个 `hlt` 桩，把 `IDTR.base` 指向它。这样 guest 的异常会变成 `HLT` 退出而不是三落。
3. **单步**：设 `RFLAGS.TF=1` 并拦截 `#DB`，可以做到"每执行一条 guest 指令就退出一次"。极慢但绝对有效，用于定位"哪一条指令触发了崩溃"。

```c
static void vcpu_single_step(vcpu_t *vc, int on)
{
    u64 rf = vmcb_rd64(vc->vmcb, VMCB_OFF_RFLAGS);
    if (on) rf |= (1ull << 8); else rf &= ~(1ull << 8);
    vmcb_wr64(vc->vmcb, VMCB_OFF_RFLAGS, rf);
    /* 必须同时拦截 #DB（vector 1），否则 TF 产生的 #DB 会直接进 guest */
    vc->intercept_exceptions |= (1u << 1);
    vmcb_wr32(vc->vmcb, VMCB_OFF_IEXCP, vc->intercept_exceptions);
}
```

## 18.8 回归测试：用"退出次数"当断言

性能与正确性都可以用一个指标卡住：**进入 guest 到出现某个标记字符串，总共多少次退出**。

```c
typedef struct {
    const char *marker;     /* 期望出现在串口输出里的字符串 */
    u32 max_exits;          /* 超过这个数就算失败（防止死循环） */
} vmtest_t;

static const vmtest_t g_tests[] = {
    { "GUEST: hello from cunos VMM", 200 },     /* 阶段 1 */
    { "Linux version",               20000 },   /* 阶段 3：内核开始打印 */
    { "Freeing unused kernel memory", 200000 }, /* 阶段 3：进入用户态 */
    { "login:",                      800000 },  /* 阶段 4：到登录提示 */
};
```

串口输出里抓标记的实现：在 `serial_putc` 里做滑动匹配（40 字节窗口），命中就记 `g_marker_hits`。**有了这个，整个项目就有了"自动化验收"**——每次改动后跑一遍，看四个阶段分别在第几次退出时命中。

## 18.9 建议的验证节奏

| 阶段 | 验证动作 | 通过判据 |
|---|---|---|
| 阶段 0 | 真机跑 `svm_probe` + `svm_enable` | 串口打印出 SVM rev 与 EFER 位 |
| 阶段 1 | `vm hello` | 出现 `GUEST: hello`，`hlt=1` |
| 阶段 2 | `vm hello` 换成带 PIT/键盘的 guest | guest 能收到 IRQ0，且 `io` 计数可控 |
| 阶段 3 | `vm debian` | 出现 `Linux version`，再到 `Freeing unused kernel memory` |
| 阶段 4 | 同上 + 交互 | `login:` 出现，能敲入用户名 |
| 阶段 5 | 同上 + 图形 | 屏幕上有 guest 画面，鼠标能点 |
