# 第 15 章 客户机引导方案：SeaBIOS 还是自写直引导 loader

## 15.1 为什么"引导"是最容易低估的一步

从"VMCB 里 RIP 指向一段我们写的代码"到"Debian 内核起来了"，中间隔着一整套 PC 固件约定：实模式进入、`int 0x13` 读盘、`int 0x15` 取内存图、`int 0x10` 设显示模式、把内核搬到 `0x100000`、跳转到保护模式入口、传 `boot_params`、加载 initrd。**每一步都由 guest 侧固件完成**，而我们没有固件。

只有两条路：把固件搬进来（SeaBIOS），或者自己扮演固件（直引导 loader）。

## 15.2 路线 A：移植 SeaBIOS

SeaBIOS 是一个 16 位实模式的 BIOS 实现，编译后约 128KB 的 ROM 镜像，放在 `0xFFF00000`–`0xFFFFFFFF`。

移植需要做的事：

| 项 | 说明 | 工作量 |
|---|---|---|
| ROM 镜像放置 | 编译 SeaBIOS（`make` 需要 gcc + iasl），把 `bios.bin` 写进 guest RAM 的 `0xFFF00000` 并把 NPT 映射上 | 小 |
| 复位向量 | guest 从 `0xFFFFFFF0` 开始执行（CS base = `0xFFFF0000`），需要 VMCB 里正确设置 CS/CS.base 与 RIP | 小 |
| **BIOS 后端服务** | SeaBIOS 通过 `int 0x13/0x15/0x16/0x10/0x1A` 向"硬件"要服务，这些中断的处理代码在 SeaBIOS 里，但它要通过**端口 IO / 内存映射**访问真实硬件。因此我们仍须实现 IDE 控制器、PIC、PIT、键盘、VGA——**一个都不能少** | **大** |
| 与 virtio 的对接 | SeaBIOS 支持 `virtio-blk` 引导（有 `virtio-blk` 驱动），但要求 virtio 设备在 PCI 上正确枚举、且 legacy 接口完全合规 | 中 |
| 调试 | SeaBIOS 的日志走 `0x402` 调试口，我们需要实现它才能看到输出 | 小 |
| 运行成本 | SeaBIOS 启动过程会产生**数千次 IOIO 退出**（逐字节 PIO 读盘、逐次 PIC 初始化） | 大（性能） |

一句话总结：**SeaBIOS 不能"替我们实现设备"，它只是"用更复杂的方式要求我们实现设备"。** 它换来的是"兼容性"（连 DOS 都能跑），代价是"我们必须先有一台完整的 PC"。

## 15.3 路线 B：自写 32 位直引导 loader（跳过实模式）

关键洞察：**Linux 内核有"32 位保护模式引导协议"**。它允许引导器直接把 CPU 置于保护模式、把内核放在 `0x100000`、填好 `boot_params`，然后跳到内核入口——**完全不需要实模式、不需要 `int 0x13`、不需要 BIOS**。

这条协议存在的原因，正是"引导器不想写实模式代码"（现代 UEFI 引导器就用这个入口）。

需要满足的前置条件（这是本章的技术核心）：

1. **CPU 处于 32 位保护模式**，段寄存器全部为平坦段（base=0，limit=`0xFFFFFFFF`，32 位），`CR0.PE=1`，`CR0.PG=0`（内核会自己开分页）。
2. **`ESI` 指向 `boot_params`（"零页"）的物理地址**。
3. **`boot_params` 至少填四块**：`e820` 内存图（`e820_entries` + 表项）、`cmd_line_ptr` + `cmd_line_size`、`hdr`（把内核自己的 `setup_header` 拷进来）、`initrd_addr_max`。
4. **内核镜像已按 `LOADED_HIGH` 方式解压到位**：`code32_start`（通常 `0x100000`）处是解压后的保护模式内核。
5. **initrd 已在内存中**，`ramdisk_image` / `ramdisk_size` 指向它。
6. **中断关闭**（`IF=0`），`IDT` 无效也没关系（内核会重设）。

对我们的意义：**这套流程完全可以在 VMM 的 C 代码里完成**——因为"在 guest 内存里构造 `boot_params`"就是往 `ram_va(...)` 里写结构体。

```c
/* 直引导：在 guest 内存里搭好 boot_params，然后把 VMCB 置为 32 位平坦保护模式 */
int vm_boot_bzimage(vm_t *vm, const u8 *bzimage, u32 bz_len,
                    const u8 *initrd,  u32 initrd_len,
                    const char *cmdline)
{
    /* 1) 解析 setup header：不硬编码偏移，用 magic 扫描（见 15.5） */
    bz_hdr_t h;
    if (bz_parse_header(bzimage, bz_len, &h) < 0) return -1;

    /* 2) 解压内核到 GPA 0x100000（内核自带的 gunzip 在实模式路径里，
     *    32 位协议下要求引导器给的是"已解压内核"，
     *    因此我们需要在宿主侧实现 inflate —— 见 15.4 的取舍说明 */
    u32 kern_len = h.payload_len;
    if (0x100000u + kern_len > vm->ram_size) return -1;
    if (inflate_to(bzimage + h.payload_off, h.payload_comp_len, ram_va(0x100000)) < 0) return -1;

    /* 3) initrd 放到"高端"（避开内核解压后的 bss 预留），2MB 对齐 */
    u32 initrd_gpa = (vm->ram_size - initrd_len) & ~0x1FFFFFu;
    memcpy(ram_va(initrd_gpa), initrd, initrd_len);

    /* 4) boot_params 放在 0x90000（传统位置，1 页足够；实际结构 ~4KB） */
    u8 *bp = (u8 *)ram_va(0x90000);
    memset(bp, 0, 4096);
    boot_params_fill(bp, vm, initrd_gpa, initrd_len, cmdline);

    /* 5) 把 VMCB 置为 32 位平坦保护模式，ESI = boot_params 物理地址 */
    vcpu_init_flat32(vm->vcpus, 0x100000u /* code32_start */, 0x90000u /* 栈 */);
    vmcb_wr32(vm->vcpus->vmcb, VMCB_OFF_RSI, 0x90000u);

    return vm_run(vm);
}
```

## 15.4 直引导的真实难点：内核解压

32 位协议要求"内核已经是解压后的形态"。而 Debian 的 `vmlinuz` 是**压缩过的 bzImage**（里面含一段自解压代码，靠实模式的 `startup_32` 之前的 `decompress_kernel` 完成）。

三条应对：

| 方案 | 做法 | 评价 |
|---|---|---|
| **宿主侧实现 inflate** | 在 cunos 里实现一个 DEFLATE 解压器（约 500 行） | 一次性工作，之后可以直接吃 `vmlinuz`，**推荐** |
| 宿主侧预解压 | 在构建镜像时（PC 上）用 `extract-vmlinux` 之类的工具把内核解压成 ELF/vmlinux，再嵌入 | 简单，但把"必须用外部工具"引入构建链 |
| 走实模式路径 | 让内核自己的解压代码跑（需要实模式 + `int 0x15` 等服务） | 又回到 SeaBIOS 的问题 |

**推荐第一种**：cunos 已经有 `ext2.c`（读文件）与 `ata.c`（读盘），再加一个 inflate 就能"从 ext2 镜像里直接读 `vmlinuz` 并引导"。这也顺带解决了"内核与 initrd 从哪来"的问题——它们就是宿主磁盘上的两个普通文件。

## 15.5 不硬编码偏移：用 magic 扫描解析 setup header

`setup_header` 的字段偏移在不同内核版本间有过变动，硬编码 `0x214` 这类偏移是**必然要踩的坑**。稳健做法：

```c
/* bzImage 的 setup 区从偏移 0 开始，长度 = (setup_sects + 1) * 512。
 * "HdrS" magic 位于 setup 区的固定相对位置，用它定位 header 起点。 */
#define HDRS_MAGIC 0x53726448u   /* 'HdrS' */

typedef struct {
    u32 setup_sects;
    u32 code32_start;
    u32 payload_off;        /* 保护模式内核在 bzImage 内的偏移 */
    u32 payload_len;        /* 解压后长度（由 header 的 syssize 推算或由 inflate 输出） */
    u32 payload_comp_len;
    u8  loadflags;
} bz_hdr_t;

int bz_parse_header(const u8 *img, u32 len, bz_hdr_t *out)
{
    for (u32 i = 0x1F0; i < 0x300 && i + 4 <= len; i++) {
        if (*(const u32 *)(img + i) == HDRS_MAGIC) {
            /* 找到了 header 的 magic。它前面的字段布局是固定的相对关系，
             * 但本文不在此硬编码绝对偏移——而是把 "magic 位置" 作为锚点，
             * 后续字段按 【需核对：boot.rst / bootparam.h】 的相对偏移读取。 */
            u32 hdr_off = i - 4;                 /* HdrS 前 4 字节是 jump 指令 */
            u8  setup_sects = img[0x1F1];        /* 这一项在所有版本都固定在 0x1F1 */
            out->setup_sects = setup_sects ? setup_sects : 4;
            out->payload_off = (out->setup_sects + 1) * 512;
            /* code32_start / syssize / loadflags 的相对偏移见上表，
               必须按目标内核版本核对后填入 */
            return 0;
        }
    }
    return -1;
}
```

**必须核对的三处**（写进项目 TODO，不许凭记忆填）：`code32_start`、`syssize`（解压后大小，需乘 16）、`loadflags.LOADED_HIGH`。

## 15.6 两条路线的最终对比

| 维度 | SeaBIOS | 自写直引导 loader |
|---|---|---|
| 前期工作量 | 中（编译 + 部署 + 调试口） | 中（boot_params 构造 + inflate） |
| 依赖的设备 | **全套**：IDE、PIC、PIT、VGA、键盘都必须对 | **极少**：阶段 3 只要 UART + 块设备（甚至可以先只用 initrd 不用盘） |
| 首次成功的退出次数 | 数千（PIO 逐字节） | 数十（一次 memcpy 完事，全在宿主侧） |
| 能否引导 DOS/老系统 | 能 | 不能（只认 Linux 32 位协议） |
| 对 Debian 的支持 | 强（SeaBIOS 对 Debian 的经验丰富） | 强（Debian 内核支持 32 位协议） |
| 调试友好度 | 差（问题藏在固件里） | 好（每一步都是我们的 C 代码，都能打日志） |
| 与我们的目标匹配度 | 低（我们只要 Linux） | **高** |

**结论：阶段 3 走直引导 loader。** 把 SeaBIOS 留作"阶段 5 的可选增强"，用于"想跑非 Linux 系统"的场景。
