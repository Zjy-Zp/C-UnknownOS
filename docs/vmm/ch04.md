# 第 4 章 AMD-V（SVM）硬件机制详解

## 4.1 为什么 32 位保护模式宿主可以用 SVM

这是整份设计的前提，必须先钉死：**SVM 不要求长模式**。VMCB 的 state save area 里，通用寄存器以 64 位槽位存放，32 位宿主/32 位 guest 只使用低 32 位（`RAX` 槽的低半即 `EAX`）；段寄存器以"selector + attrib + limit + base"的 legacy 形式完整描述，正是 386 保护模式需要的形态。只要 `EFER.LMA = 0`，VMRUN 就是在两个 32 位保护模式上下文之间切换。

对 cunos 而言，这意味着不需要先做长模式移植（那本身是一个几百行的工程），可以**直接在现有的 32 位分页模型上落地 VMM**。【需核对：APM Vol.2 Appendix B 中关于 legacy 模式下 VMRUN 的说明，以及各寄存器槽位在 32 位模式下的有效宽度】

## 4.2 探测：CPUID

```c
/* vmm/svm.c —— 能力探测，返回 0 表示不可用 */
#define CPUID_FN_EXT_MAX     0x80000000u
#define CPUID_FN_SVM_FEAT    0x80000001u   /* ECX[2] = SVM */
#define CPUID_FN_SVM_INFO    0x8000000Au   /* EBX = NASID, EDX = 特性位 */

typedef struct {
    u32 nasid;        /* 可用 ASID 数量，ASID 有效值与 0 保留 */
    u32 svm_rev;      /* SVM 版本（低 8 位） */
    u32 has_npt;      /* EDX[0] */
    u32 has_lbr;      /* EDX[1] */
    u32 has_svmlock;  /* EDX[2] */
    u32 has_nrips;    /* EDX[3]：Next-RIP 保存，32 位下基本用不到 */
    u32 has_cleanbits;/* EDX[5]：VMCB clean bits */
    u32 has_flush_asid;/* EDX[6]：支持 INVLPGA 按 ASID 刷 */
    u32 has_decode_assist; /* EDX[7] */
    u32 has_avic;     /* EDX[13] 【需核对位号】 */
} svm_caps_t;

static inline void cpuid(u32 leaf, u32 *a, u32 *b, u32 *c, u32 *d)
{
    __asm__ volatile("cpuid"
                     : "=a"(*a), "=b"(*b), "=c"(*c), "=d"(*d)
                     : "a"(leaf), "c"(0));
}

int svm_probe(svm_caps_t *out)
{
    u32 a, b, c, d;

    memset(out, 0, sizeof(*out));
    cpuid(CPUID_FN_EXT_MAX, &a, &b, &c, &d);
    if (a < CPUID_FN_SVM_FEAT) {
        serial_puts("SVM: no extended CPUID\n");
        return -1;
    }
    cpuid(CPUID_FN_SVM_FEAT, &a, &b, &c, &d);
    if (!(c & (1u << 2))) {                 /* ECX[2] = SVM */
        serial_puts("SVM: CPUID says no SVM (Intel CPU or disabled)\n");
        return -1;
    }
    cpuid(CPUID_FN_SVM_INFO, &a, &b, &c, &d);
    out->nasid            = b;              /* EBX = NASID */
    out->svm_rev          = a & 0xFF;
    out->has_npt          = d & (1u << 0);
    out->has_lbr          = (d >> 1) & 1u;
    out->has_svmlock      = (d >> 2) & 1u;
    out->has_nrips        = (d >> 3) & 1u;
    out->has_cleanbits    = (d >> 5) & 1u;
    out->has_flush_asid   = (d >> 6) & 1u;
    out->has_decode_assist= (d >> 7) & 1u;

    serial_puts("SVM: rev=0x"); serial_hex(out->svm_rev);
    serial_puts(" nasid=");     serial_dec(out->nasid);
    serial_puts(" npt=");       serial_dec(out->has_npt);
    serial_puts(" clean=");     serial_dec(out->has_cleanbits);
    serial_putc('\n');

    if (!out->has_npt) {
        /* 没有 NPT 就只能用"影子页表"路线，工作量翻倍且极易错。
         * cunos 直接放弃：这是硬性门槛。 */
        serial_puts("SVM: NPT required, abort\n");
        return -1;
    }
    return 0;
}
```

三个必须记住的点：

1. **CPUID 说"支持"不等于"可用"**。BIOS/固件可以在 `VM_CR` 里把 SVM 禁掉（见 4.3），Hyper-V 之类的宿主也可能在它自己的 guest 里屏蔽 `CPUID.80000001.ECX[2]`。这正是"在 QEMU 里测 SVM"必然失败的第一个原因（第 18.4 节详述）。
2. **NASID 是 ASID 的上界**，实际可用 ASID 是 `1..NASID-1`，0 是保留值（表示"必须刷全部 TLB"）。
3. **`CPUID.8000000A.EDX[0]`（NPT）必须为 1**。cunos 不做影子页表。

## 4.3 启用：EFER.SVME 与 VM_CR

```c
#define MSR_EFER        0xC0000080u
#define MSR_VM_CR       0xC0010114u
#define MSR_VM_HSAVE_PA 0xC0010117u

#define EFER_SVME       (1u << 12)

static inline u64 rdmsr(u32 msr)
{
    u32 lo, hi;
    __asm__ volatile("rdmsr" : "=a"(lo), "=d"(hi) : "c"(msr));
    return ((u64)hi << 32) | lo;
}

static inline void wrmsr(u32 msr, u64 val)
{
    u32 lo = (u32)val, hi = (u32)(val >> 32);
    __asm__ volatile("wrmsr" : : "c"(msr), "a"(lo), "d"(hi));
}

int svm_enable(void)
{
    u64 vmcr = rdmsr(MSR_VM_CR);

    /* SVMDIS 位：置 1 表示固件禁用了 SVM。位号与其余位（LOCK/INVD 等）
     * 在不同 APM 修订版里表述有差异，必须核对后填常量。 */
    if (vmcr & (1ull << 4)) {              /* 【需核对：VM_CR.SVMDIS 位号】 */
        serial_puts("SVM: disabled by firmware (VM_CR.SVMDIS)\n");
        return -1;
    }

    u64 efer = rdmsr(MSR_EFER);
    if (!(efer & EFER_SVME)) {
        efer |= EFER_SVME;
        wrmsr(MSR_EFER, efer);
        efer = rdmsr(MSR_EFER);
        if (!(efer & EFER_SVME)) {
            serial_puts("SVM: EFER.SVME write ignored\n");
            return -1;
        }
    }
    serial_puts("SVM: enabled, EFER=0x");
    serial_hex((u32)efer);
    serial_putc('\n');
    return 0;
}
```

工程要点：

- **EFER 在 32 位模式下可写**（`MSR 0xC0000080` 不是长模式专属），但 `EFER.LME` 一旦置位并开启分页就会进入长模式，因此 **绝不能顺手把 EFER 整体赋值**，只能读-改-写目标位。这是"32 位宿主写 MSR 最容易自杀的地方"。
- `EFER.NXE`（bit 11）只在 PAE/长模式页表下才有意义。cunos 用的是非 PAE 且 PTE 只有 32 位，**没有 NX 位**，所以无需关心；但 **NPT 表项是 64 位格式，含 NX 位**，若要给 NPT 表项置 NX，需确认 `EFER.NXE` 是否必须为 1——【需核对】。
- `VM_CR` 的写权限：多数平台该 MSR 在固件初始化后被锁（LOCK 位），宿主无法改写，只能读出来判断。因此 `svm_enable()` **只读不写**，避免 `#GP`。

## 4.4 HSAVE 页

`VM_HSAVE_PA`（`0xC0010117`）指向一个 4KB 页，专门存放"宿主上下文快照"：

- `VMRUN` 时，硬件把**宿主**的 RIP/RSP/RFLAGS/段寄存器/CR 等写入该页；
- `#VMEXIT` 时，硬件从该页恢复宿主上下文；
- 因此宿主从 `VMRUN` 的下一条指令继续执行，栈没有切换（仍在宿主内核栈上）。

约束：

1. 物理页、4KB 对齐、全零初始化。
2. **每个 vCPU 一个 HSAVE 页**。`VM_HSAVE_PA` 是 per-CPU MSR（在 cunos 的单核场景下等价于 per-vCPU），切换 vCPU 前必须改写该 MSR 指向新页。若共用一页，两个 vCPU 交替运行会互相覆盖宿主快照，症状是随机三落（triple fault）或回到错误的 RIP。
3. 该页内容对软件**不可解析**（布局隐式），不要试图读写。

```c
static u32 g_hsave_pa;   /* 4KB 对齐 */

int svm_hsave_alloc(void)
{
    u32 pa = vmm_ctl_alloc_page();      /* 见 8.5，专用控制池 */
    if (!pa) { serial_puts("SVM: no HSAVE page\n"); return -1; }
    g_hsave_pa = pa;
    wrmsr(MSR_VM_HSAVE_PA, (u64)pa);
    if ((u32)rdmsr(MSR_VM_HSAVE_PA) != pa) {
        serial_puts("SVM: VM_HSAVE_PA write failed\n");
        return -1;
    }
    serial_puts("SVM: HSAVE=0x"); serial_hex(pa); serial_putc('\n');
    return 0;
}
```

## 4.5 VMCB 内存布局

VMCB 是 4KB、4KB 对齐的物理内存，`VMRUN` 的 EAX（32 位下）必须填它的**物理地址**。它被切成两半：

| 区域 | 偏移范围 | 内容 | 谁写 |
|---|---|---|---|
| control area | `0x000–0x3FF` | 拦截位图、IOPM/MSRPM 物理地址、ASID、中断注入控制、nCR3、退出信息 | 宿主（主要） |
| state save area | `0x400–0xFFF` | guest 的段寄存器、CR/EFER、RIP/RSP/RFLAGS、通用寄存器、CR2 | 宿主初始化，硬件在 guest 执行中持续更新 |

### 4.5.1 control area 关键字段

下表是 cunos 需要触碰的字段（不需要的字段一律保持 0 并由 4KB 清零保证）。**【标注"需核对"的项必须逐个用 `offsetof` 与实际 APM 表格比对】**

| 偏移 | 宽度 | 字段 | 含义 / cunos 用法 |
|---|---|---|---|
| `0x000` | u16 | `intercept_cr_read` | bit i 置 1 → 读 CRi 退出；cunos 只拦 CR3（bit3）与 CR0/CR4 的写入 |
| `0x002` | u16 | `intercept_cr_write` | 同上，写方向 |
| `0x004` | u16 | `intercept_dr_read` | 调试寄存器读拦截；cunos 全 0（阶段 1-3） |
| `0x006` | u16 | `intercept_dr_write` | 同上 |
| `0x008` | u32 | `intercept_exceptions` | bit i 置 1 → guest 的异常向量 i 退出；cunos 只拦 `#UD`(6)、`#GP`(13)、`#PF`(14)、`#AC`? 阶段 2 只拦 6/13/14 |
| `0x00C` | u32 | `intercept` | 杂项拦截：中断/异常注入、`HLT`、`INTR`、`NMI`、`SMI`、`SHUTDOWN`、`VMRUN` 等（位号见 4.5.3） |
| `0x040` | u64 | `iopm_base_pa` | IOPM 物理地址（12KB = 64K bit / 8） |
| `0x048` | u64 | `msrpm_base_pa` | MSRPM 物理地址（12KB，MSR 空间按 2 段位图映射） |
| `0x050` | u64 | `tsc_offset` | TSC 偏移；cunos 初期置 0，阶段 4 用它给 guest 一个稳定 TSC |
| `0x058` | u32 | `asid` | 地址空间标识，见 4.7 |
| `0x05C` | u8 | `tlb_ctl` | 0=不刷；1=刷全部；3=按 ASID 刷；4=……【需核对取值】；cunos 每次 VMRUN 前置 0（靠 NPT 与 TLB 语义保证正确，见 6.5） |
| `0x060` | u32 | `int_ctl` | 中断注入控制：`V_IRQ`、`V_TPR`、`V_INTR_MASKING`、`V_IGN_TPR` 等位【需核对位布局】 |
| `0x064` | u32 | `int_vector` | 待注入的中断向量号 |
| `0x068` | u32 | `int_state` | 中断注入队列状态（只读） |
| `0x070` | u32 | `exit_code` | 退出码；`#VMEXIT` 后由硬件写入 |
| `0x074` | u32 | `exit_code_hi` | 退出码高位（cunos 用不到，保持 0） |
| `0x078` | u64 | `exit_info_1` | 语义随退出码变化 |
| `0x080` | u64 | `exit_info_2` | 语义随退出码变化 |
| `0x088` | u32 | `exit_int_info` | 若退出由异常引起，这里给出异常向量与错误码编码 |
| `0x08C` | u32 | `exit_int_info_err` | 上述异常的错误码 |
| `0x090–0x09F` | — | （nested paging / AVIC 相关） | cunos 不使用，保持 0【需核对：nested_ctl 与 avic_apic_bar 的确切偏移】 |
| `0x0A0` | u64 | `eventinj` | 事件注入（异常/中断注入的统一入口），格式见 4.6.2【需核对偏移】 |
| `0x0A8` | u64 | `n_cr3` | NPT 根表物理地址（第二级翻译的 CR3）【需核对偏移】 |
| `0x0B0` | u64 | `lbr_ctl` | LBR 虚拟化；cunos 保持 0 |
| `0x0C8` | u32 | `clean_bits` | clean 位图（见 4.8）【需核对偏移】 |
| `0x0CC` | u32 | `clean` | clean 位写窗口（写 1 表示对应组已加载）【需核对偏移】 |

### 4.5.2 state save area 布局

段寄存器（ES/CS/SS/DS/FS/GS/LDTR/TR）与描述符表寄存器（GDTR/IDTR）都是 16 字节的固定格式：

```c
typedef struct {
    u16 selector;   /* +0x0：段选择子 */
    u16 attrib;     /* +0x2：压缩属性位（见下） */
    u32 limit;      /* +0x4：段限长 */
    u64 base;       /* +0x8：段基址（32 位模式下只用低 32 位） */
} vmcb_seg_t;       /* 16 字节 */
```

`attrib` 的位定义与段描述符高 4 字节的对应关系（**这是最容易写错的地方**）：

| 位 | 名称 | 含义 |
|---|---|---|
| `3:0` | type | 段类型（代码段 `1010`=可执行可读、数据段 `0010`=可读写） |
| `4` | S | 1=代码/数据段，0=系统段 |
| `6:5` | DPL | 特权级 |
| `7` | P | 存在位 |
| `8` | AVL | 可用位 |
| `9` | L | 长模式代码段（32 位模式下必须 0） |
| `10` | D/B | 默认操作数/栈宽度（32 位段置 1） |
| `11` | G | 粒度（1=4KB） |

也就是说：一个"32 位、可读可执行、DPL0、存在、G=1、limit=4GB"的代码段，`attrib = 0x0C9B`；对应的数据段 `attrib = 0x0C93`。这两个常数会在第 11 章的 guest 初始化里反复出现。

固定偏移表（**全部需与 APM 图 15-x 对照，本文标注把握度**）：

| 偏移 | 宽度 | 字段 | 把握度 |
|---|---|---|---|
| `0x400` | 16 | `ES` | 高 |
| `0x410` | 16 | `CS` | 高 |
| `0x420` | 16 | `SS` | 高 |

| `0x4B0` | u8 | `CPL` | 【需核对：有资料写 `0x4B0`，也有写 `0x4D0` 附近，必须实测】 |
| `0x4D0` | u64 | `EFER` | 中高 |
| `0x4E0` | u64 | `CR4` | 高 |

**不用背这张表**。落地做法是把它写成结构体 + 静态断言，让编译器替你背：

```c
/* vmm/vmcb.h */
#define VMCB_OFF_ES     0x400
#define VMCB_OFF_CPL    0x4B0
#define VMCB_OFF_EFER   0x4D0
#define VMCB_OFF_CR0    0x4F0
#define VMCB_OFF_RIP    0x510
#define VMCB_OFF_RAX    0x530
/* ... 其余同理 ... */

typedef struct { u8 b[4096]; } vmcb_raw_t;

/* 用"字节偏移访问器"而不是结构体成员，原因见正文 4.5.3 */
static inline u64 *vmcb_ptr64(u8 *vmcb, u32 off) { return (u64 *)(vmcb + off); }
static inline u32 *vmcb_ptr32(u8 *vmcb, u32 off) { return (u32 *)(vmcb + off); }
```

> **为什么不直接定义 `struct vmcb`？** 因为一旦把"文档可能写错的偏移"固化进结构体成员，任何偏移错误都变成"到处都在读写错误位置"，且编译器不会报警。用**显式字节偏移 + 断言**的方式，错误只会在断言处暴露一次。断言写法：
>
> ```c
> /* 编译期对齐检查：VMCB 必须 4KB 对齐 */
> typedef char vmcb_align_check[(VMCB_SIZE == 4096) ? 1 : -1];
> ```
>
> 而"偏移是否正确"这一步只能在真机上验证——用第 18.2 节的"最小副作用探针"：先只写 `exit_code` 观察、再只写 `RIP` 观察，逐字段二分。

### 4.5.3 杂项拦截位（`0x00C`）

`intercept` 字段是 32 位，每一位对应一类"杂项事件"。cunos 阶段 2 需要打开的只有几位（其余保持 0 表示"不拦"，即 guest 直接执行）：

| 位置 1 时拦截的事件 | cunos 是否打开 | 理由 |
|---|---|---|
| `INTR`（物理中断被递送） | 否 | 宿主 IF=0，PIC 全屏蔽，不会有物理中断 |
| `INTn`（`int n` 指令） | 阶段 3 起 | 初期让 guest 自己用自己的 IDT 处理，减少退出 |
| `NMI` | 否 | 无 NMI 源 |
| `SMI` | 否 | 不可屏蔽，硬件处理 |
| `HLT` | **是** | 否则 guest `hlt` 会让物理核挂起，宿主永远拿不回控制权 |
| `SHUTDOWN` | **是** | guest 三落/关机时必须被捕获，否则宿主无法感知 |
| `VMRUN` | 是（guest 内禁止嵌套） | 防止 guest 试图自己跑 VMRUN |
| `PAUSE`（可选） | 阶段 4 | 改善 guest 自旋等待的行为 |
| `MONITOR`/`MWAIT` | 是 | cunos 不实现，直接注入 `#UD` 更简单 |

> 位的确切编号随 APM 修订版差异较大（例如 `HLT` 与 `SHUTDOWN` 的相对位置在不同资料里表述不一致），**必须核对**。落地技巧：阶段 1 只打开 `HLT` 一位，用"guest 执行 `hlt` 是否触发退出"这一个实验就能确定该位号——这比查表更快。

## 4.6 八条 SVM 指令

| 指令 | 编码 | 语义 | cunos 使用时机 |
|---|---|---|---|
| `VMRUN` | `0F 01 D8` | 用 EAX/RAX 指定的 VMCB 物理地址启动 guest；返回即意味着发生过 `#VMEXIT` | `vcpu_run()` 主循环内 |
| `VMLOAD` | `0F 01 DA` | 从 VMCB 装载 FS/GS/KernelGsBase/STAR/LSTAR/CSTAR/SFMASK/SYSENTER_* 等"MSR 类"状态 | 一般不用（VMRUN 已含）；仅在自定义 restore 路径用 |
| `VMSAVE` | `0F 01 DB` | 把上述状态存回 VMCB | 同上 |
| `STGI` | `0F 01 DC` | 置 GIF=1（允许物理中断递送给 guest） | 只在需要 guest 被外部中断打断时 |
| `CLGI` | `0F 01 DD` | 清 GIF=0（禁止递送） | 宿主初始化、退出处理期间 |
| `INVLPGA` | `0F 01 DF` | 按 ASID 刷新 guest TLB 项（EAX=虚拟地址，ECX=ASID） | guest 改页表后由其自身 `invlpg` 触发退出，宿主代为执行 |
| `SKINIT` | `0F 01 DE` | 安全启动一条链（SKINIT/SLB） | 不使用 |
| `VMMCALL` | `0F 01 D9` | guest 主动调用 hypervisor（超调用） | **阶段 2 起作为"guest 请求服务"的通道**（如打印、关机、读时钟） |

内联汇编一律 AT&T：

```c
static inline void svm_vmrun(u32 vmcb_pa)
{
    /* VMRUN 不改变宿主栈，返回时 RIP 落在下一条指令 */
    __asm__ volatile("vmrun %%eax" : : "a"(vmcb_pa) : "memory");
}
static inline void svm_stgi(void) { __asm__ volatile("stgi" ::: "memory"); }
static inline void svm_clgi(void) { __asm__ volatile("clgi" ::: "memory"); }
static inline void svm_invlpga(u32 vaddr, u32 asid)
{
    __asm__ volatile("invlpga" : : "a"(vaddr), "c"(asid) : "memory");
}
```

**VMRUN 失败路径**：如果 `EFER.SVME=0`、VMCB 未对齐、`nCR3` 未设而 NPT 被要求，VMRUN 会触发 `#UD`/`#GP`。此时宿主根本进不去 guest，而且**没有 `#VMEXIT`**。第 11.4 节给出用 IDT 挂钩 + 标志位区分"正常退出"与"启动失败"的写法。

## 4.7 GIF：一个比想象中更关键的开关

GIF 是**全局**的，不属于 guest 上下文，`VMRUN` 不会自动置位，`#VMEXIT` 会**自动清零**。它的语义是：

- `GIF=0`：物理 INTR/NMI/SMI 被"挂起"，不会递送给 guest，也不会打断 `VMRUN` 内的 guest 执行；
- `GIF=1`：允许以 guest 身份接收物理中断（会走 guest 的 IDT，但中断注入路径由硬件处理）。

cunos 的现实是：**内核从不开启 IF**（键盘/鼠标/网卡全是轮询），PIC 也没有被真正驱动。因此推荐策略是：

```
宿主初始化：CLGI  → 全程 GIF=0
vcpu_run：  不 STGI，直接 VMRUN
#VMEXIT：   硬件已清零，无需处理
```

代价是：guest 无法被真实时钟中断打断，所有"异步"都必须由虚拟设备（8254 PIT）在退出点上注入。这正好符合 cunos"无抢占、事件驱动"的体系，且**避免了"物理中断误注入 guest"这一类极难调试的问题**。

反过来说，若将来要在 vCPU 上实现抢占（阶段 5），才需要在 `VMRUN` 前 `STGI`，并保证 `#VMEXIT` 后第一时间 `CLGI`——但那样一来，PIC 必须被正确初始化和屏蔽，这是一整块额外工作。

## 4.8 ASID 与 clean/dirty 位

**ASID**：给 TLB 项打标签，使"切换 guest"不必刷全 TLB。取值 `1..NASID-1`，`0` 表示"刷全部"。cunos 只有一台 VM 时，ASID 恒定用 1。真正需要它的是"同一 VM 内多个 vCPU 共享地址空间"的场景——此时同 ASID 让它们共享 TLB 项，反而更快。**不要给每个 vCPU 分不同 ASID**，那是给"多个不同地址空间的 VM"准备的。

**clean/dirty 位**：VMCB 的 state save area 有上千字节，每次 VMRUN 全量装载是浪费。硬件提供一组"脏位"标记：宿主修改了某组字段就在 control area 的 `clean` 字段里置对应位，VMRUN 只装回被标记的组。`CPUID.8000000A.EDX[5]` 表示是否支持。

cunos 的做法：**阶段 1-3 完全不用 clean 位**（每次全量装载，正确性优先），并在 control area 的 clean 相关字段保持 0。**注意**：若不支持 clean 位，硬件会忽略这些字段；若支持而宿主持久写 0，则每次全量装载——行为一致且安全。这是一处"不用优化换正确性"的自觉取舍，第 19 章会核算它的真实成本（每次 VMRUN 多出约 1KB 的装载，量级在百纳秒级，相对于退出处理可以忽略）。

## 4.9 一张图总结 SVM 的执行流

```
宿主 ring0                                    guest（VMCB 描述的世界）
   │
   ├─ CLGI（GIF=0）
   ├─ 准备 VMCB（拦截位、nCR3、state save）
   ├─ wrmsr(VM_HSAVE_PA, hsave_pa)
   ├─ VMRUN ────────────────────────────────►  执行 guest 指令
   │                                              │
   │                                              ├─ 普通指令：继续
   │                                              ├─ 命中拦截/异常/NPF
   │                                              ▼
   │  ◄──────────────────────────────────────  #VMEXIT（GIF 自动清 0）
   ├─ 读 exit_code / exit_info1 / exit_info2
   ├─ 分发：处理 → 改 state save → 回到主循环
   └─ 再次 VMRUN
```

**只有一条主循环，只有一个出口。** 这个极简模型是整个 VMM 可维护性的来源：所有的 guest 行为都必须在这个模型下被解释，没有"另一条路径"。
