# 第 5 章 #VMEXIT 机制与退出码表

## 5.1 一次退出的完整过程

当 guest 触发被拦截的事件，硬件按固定顺序做以下动作：

1. 把 guest 当前上下文（段寄存器、RIP/RSP/RFLAGS、CR、通用寄存器中硬件负责的部分）写回 VMCB 的 state save area；
2. 清零 GIF；
3. 在 control area 写入 `exit_code`、`exit_info_1`、`exit_info_2`、`exit_int_info`；
4. 从 HSAVE 页恢复宿主上下文；
5. 把控制权交回 `VMRUN` 的下一条指令（宿主 RIP/RSP 不变）。

宿主**必须自己做的事**（这是新手最容易漏的一批）：

- **通用寄存器除 RAX 之外是否已被写回 VMCB？** 答案：是——退出时硬件把 guest 的 GPR 全量写进 state save area，包括 RAX。因此宿主处理 "guest 执行了 `in` 指令" 时，要读/写 guest 寄存器一律操作 VMCB 里的槽位，而不是宿主的寄存器。
- **宿主的 CR3 是否恢复？** 是（从 HSAVE 页），宿主页表立即生效，可以正常读写自己的内存。
- **宿主的 IF 是否恢复？** 是，但**宿主本来就是 IF=0**，无需处理。
- **NPT 的 TLB 是否需要刷？** 只有宿主改了 NPT 表项才需要（见 6.5）。
- **guest 的 RIP 是否已前推？** **否**。`in`/`out`/`rdmsr`/`cpuid` 等指令退出时，VMCB 里的 RIP 指向该指令**本身**。宿主处理完必须自己 `RIP += 指令长度`，否则 guest 会无限重复同一条指令（现象：串口刷屏同一条日志，或 guest 卡死）。

## 5.2 exit_code 的编码

| 位域 | 含义 |
|---|---|
| `15:0` | 退出号（见 5.4 表） |
| `31:16` | 错误信息：`0x8000` 表示"退出由无效 VMCB 状态引起"（如 guest 处于不可恢复状态），其余值保留【需核对】 |
| `63:32` | 保留 |

第 5 步的判据是：`(exit_code & 0xFFFF)` 用于查表分发；`(exit_code >> 16)` 非 0 时要打印告警——这通常意味着 VMCB 配置有结构性错误，而不是某个 guest 指令的小问题。

## 5.3 EXITINFO1 / EXITINFO2 的语义

| 退出类别 | `exit_info_1` | `exit_info_2` |
|---|---|---|
| `IOIO`（端口访问） | 端口号（`15:0`）+ 方向位 + 访问宽度编码 + 是否字符串指令 | — |
| `MSR` | 是否为写（1=写，0=读）；读时还带"是否已填充"标记 | 被访问的 MSR 号 |
| `NPF`（NPT 缺页，`0x400`） | 错误码位域（见 6.4） | 出错的 **guest 物理地址**（页对齐） |
| `CR read/write` | 被访问的 CR 号 | 写入时的新值 |
| `SHUTDOWN` | 关机原因编码 | — |
| 其他 | 视退出码而定，未定义时应打印原始值 |

IOIO 的方向/宽度位细节在各版 APM 中表述略有差异（尤其"访问宽度编码 0/1/2/3 分别对应 byte/word/dword/qword"这一点）**【需核对】**。工程上有一个几乎零成本的兜底手段：**同时用退出时 guest RIP 指向的指令字节（通过 NPT 窗口读 GPA）来反解操作数宽度**——

```c
/* 从退出时 guest RIP 读指令前缀/操作码，反解 IO 宽度。
 * 前提：guest 代码页在 NPT 里必然已映射，可安全读取。 */
static u32 io_width_from_insn(u32 gpa_rip, u32 *port_out, u32 *is_in)
{
    u8 op = *(u8 *)ram_va(gpa_rip);
    /* 0xE4/0xE5: in al/eax, imm8；0xEC/0xED: in al/eax, dx
     * 0xE6/0xE7: out imm8；0xEE/0xEF: out dx
     * 前缀 0x66 表示 16 位操作数（超出本文阶段 1 范围） */
    switch (op) {
    case 0xE4: *is_in = 1; *port_out = *(u8 *)ram_va(gpa_rip + 1); return 1;
    case 0xE5: *is_in = 1; *port_out = *(u8 *)ram_va(gpa_rip + 1); return 4;
    case 0xE6: *is_in = 0; *port_out = *(u8 *)ram_va(gpa_rip + 1); return 1;
    case 0xE7: *is_in = 0; *port_out = *(u8 *)ram_va(gpa_rip + 1); return 4;
    case 0xEC: *is_in = 1; *port_out = 0; return 1;   /* 端口在 DX，需读 guest EDX */
    case 0xED: *is_in = 1; *port_out = 0; return 4;
    case 0xEE: *is_in = 0; *port_out = 0; return 1;
    case 0xEF: *is_in = 0; *port_out = 0; return 4;
    default:   return 0;   /* 不认识 → 打印退出码与指令字节，停止推进 */
    }
}
```

这段"用指令字节反解"的做法价值很高：它把"我有没有记错 EXITINFO1 位域"这个不确定性，转化为"两条独立信息源是否一致"的可验证事实。阶段 2 上线时，建议同时计算两者并断言一致，跑通 1000 次 IO 退出无告警后再切换为只信 EXITINFO1。

## 5.4 退出码表

下表列出 cunos 会遇到的退出码（编号**必须**与 APM Appendix C 核对；标"处理策略"的列为本文的设计决策）。

| 退出码 | 名称 | 触发条件 | cunos 阶段 | 处理策略 |
|---|---|---|---|---|
| `0x000`–`0x00F` | CR read（CR0..CR15） | 对应 CR 读被拦截 | 2 | 从 VMCB 取值写 guest 目标寄存器；`RIP += 2`（`mov r32, crN`） |
| `0x010`–`0x01F` | CR write | 对应 CR 写被拦截 | 2 | 校验后写回 VMCB；CR0/CR4 的保留位必须原样保留 |
| `0x020`–`0x02F` | DR read | 调试寄存器读 | 3 | 返回 0 并告警（cunos 不支持硬件断点） |
| `0x030`–`0x03F` | DR write | 调试寄存器写 | 3 | 静默忽略 |
| `0x040` | `#UD`（无效指令） | 拦截位置 1 | 2 | 注入 `#UD` 给 guest（`eventinj`）；不可直接跳过 |
| `0x041`–`0x05F` | 异常向量 1..0x1F | 对应异常被拦截 | 2 | 逐类决定：`#PF` 自行处理，其余原样注入 |
| `0x060` | INTR | 物理中断被递送 | 不打开 | 永不出现（GIF=0） |
| `0x061` | NMI | NMI | 不打开 | 同上 |
| `0x062` | SMI | SMI | 不打开 | 同上 |
| `0x063` | INIT | INIT 信号 | 不打开 | 同上 |
| `0x064` | VINTR | 虚拟中断被递送（`int_ctl.V_IRQ`） | 4 | guest 已接受中断，清 `V_IRQ` |
| `0x066` | RDTSC | 拦截位置 1 | 3 | 返回合成的 TSC（`tsc_offset` + 宿主 TSC） |
| `0x067` | RDPMC | 拦截位置 1 | 3 | 返回 0 或注入 `#GP` |
| `0x068` | PUSHF | 拦截位置 1 | 否 | 不打开（性能杀手） |
| `0x069` | POPF | 拦截位置 1 | 否 | 不打开 |
| `0x06A` | **CPUID** | 拦截位置 1 | **1（必须）** | 见 12.2：按白名单返回，**绝不能真执行**（会把宿主 CPU 信息泄露给 guest） |
| `0x06B` | RSM | 拦截位置 1 | 3 | 注入 `#GP` |
| `0x06C` | IRET | 拦截位置 1 | 否 | 不打开 |
| `0x06D` | SWINT（`int n`） | 拦截位置 1 | 3（可选） | 初期不打开，让 guest 用自己的 IDT |
| `0x06E` | INVD | 拦截位置 1 | 3 | 注入 `#GP`（INVD 会破坏宿主缓存一致性） |
| `0x06F` | PAUSE | 拦截位置 1 | 4 | 让出时间片后继续 |
| `0x070` | **HLT** | 拦截位置 1 | **1（必须）** | 见 12.3：置"guest 空闲"，退出到宿主，由 PIT 到期或外部事件唤醒 |
| `0x071` | INVLPG | 拦截位置 1 | 3 | 代为执行 `invlpg` + 刷 NPT 相关项 |
| `0x072` | INVLPGA | 拦截位置 1 | 3 | 返回；不影响宿主 |
| `0x073` | **IOIO** | IOPM 位图命中 | **1（必须）** | 见 12.4：查设备表 → 读/写 guest 寄存器 → `RIP += 指令长度` |
| `0x074` | **MSR** | MSRPM 命中 | **1（必须）** | 见 12.5：白名单（EFER/CR_PAT/SYSENTER_*/STAR/LSTAR/CSTAR/SFMASK），其余注入 `#GP` |
| `0x075` | TASK_SWITCH | 任务门切换 | 3 | 注入 `#GP`（cunos guest 不支持硬件任务切换） |
| `0x076` | FERR_FREEZE | x87 异常冻结 | 否 | 不打开 |
| `0x077` | **SHUTDOWN** | guest 三落/关机 | **1（必须）** | 见 12.6：打印原因、销毁 vCPU、回到宿主 shell |
| `0x078` | VMRUN | guest 执行 VMRUN | 2 | 注入 `#UD`（禁止嵌套） |
| `0x079` | VMMCALL | guest 主动超调用 | 2 | 超调用分发（打印/关机/取时间） |
| `0x07A` | VMLOAD | guest 执行 VMLOAD | 2 | 注入 `#UD` |
| `0x07B` | VMSAVE | guest 执行 VMSAVE | 2 | 注入 `#UD` |
| `0x07C` | STGI | guest 执行 STGI | 2 | 注入 `#UD` |
| `0x07D` | CLGI | guest 执行 CLGI | 2 | 注入 `#UD` |
| `0x07E` | SKINIT | guest 执行 SKINIT | 2 | 注入 `#UD` |
| `0x07F` | RDTSCP | 拦截位置 1 | 3 | 合成返回值（TSC + TSC_AUX） |
| `0x080` | ICEBP | `int1` | 3 | 注入 `#DB` |
| `0x081` | WBINVD | 拦截位置 1 | 3 | 注入 `#GP`（或静默假装成功） |
| `0x082` | MONITOR | 拦截位置 1 | 2 | 注入 `#UD` |
| `0x083` | MWAIT | 拦截位置 1 | 2 | 注入 `#UD` |
| `0x084` | MWAIT_COND | 拦截位置 1 | 2 | 注入 `#UD` |
| **`0x400`** | **NPF（NPT 缺页）** | guest 访问未映射的 GPA | **1（必须）** | 见 6.4：解析 `exit_info_1` 错误码，映射/注入缺页 |
| `0x401` | AVIC_INCOMPLETE_IPI | AVIC 未启用时收到 IPI | 不适用 | 不使用 AVIC |
| `0x402` | AVIC_NOACCEL | APIC 访问未加速 | 不适用 | 不使用 AVIC |

> 表中"阶段"列的含义：`1` = 阶段 1 最小闭环必须实现；`2` = 能跑自写 loader/小型 guest 必须；`3` = 跑 Debian 内核必须；`4` = 性能/交互优化必需；`否` = 不打开该拦截，永不出现。
>
> 若某个未预见退出码出现，**统一策略**是：打印退出码、`exit_info_1/2`、guest RIP/CS、然后**把 vCPU 标记为 faulted 并退出主循环**。绝对不要"猜一个处理方式然后继续跑"——在裸机上，继续跑的代价通常是几分钟后出现一个与本因无关的三落。

## 5.5 退出次数预算：为什么这决定了架构

退出是虚拟化中最贵的事。一次 `#VMEXIT` + 分发的真实成本在**数百纳秒到数微秒**（取决于宿主是否踩了 cache miss、是否跨页表），本文按 **1–3 μs** 估算（依据：SVM 退出的公开量级数据 + cunos 无优化编译，**非实测**）。

用这个数字反推设计约束：

| 场景 | 退出频率（估） | 每秒退出数 | 占比（按 2μs） | 结论 |
|---|---|---|---|---|
| 阶段 1 hello（纯串口输出） | 每字符 1 次 IO | ~50 | 0.01% | 无所谓 |
| 阶段 2 loader + 自写 guest | 串口 + PIC 初始化 + PIT | ~500 | 0.1% | 无所谓 |
| 阶段 3 Debian 引导（每 tick 一次 PIT 退出） | 100Hz × 1 | 100 | 0.02% | 无所谓 |
| 阶段 4 Debian 用户态空闲（`hlt` 循环 + tick） | 100Hz | 100 | 0.02% | 无所谓 |
| **陷阱：不打开 `PUSHF`/`POPF` 拦截但打开了 `RDTSC`** | Debian 内核每调度一次 `rdtsc` | 可达 10⁵ | **20%+** | 必须改成合成 TSC 而非退出 |
| **陷阱：IOPM 全 0（不拦任何端口）** | guest 直接操作真实硬件端口 | 0 | 0 | **更糟：guest 与宿主抢硬件** |

表格最后两行是本文最重要的两个非显然结论：

1. **不能"什么都不拦"**。IOPM 全 0 时 guest 的 `out` 会真的打到物理芯片组上，宿主与 guest 争夺同一颗 8254/8259，症状是"时钟乱跳 + 键盘乱码"，且极难想到是虚拟化问题。
2. **不能"什么都拦"**。`rdtsc`/`pushf` 这类指令在 guest 里执行频率极高，全拦会把机器拖到不可用。正确做法是**只拦"设备与安全相关"的**（IO/MSR/CPUID/HLT/SHUTDOWN），其余放任直通。

## 5.6 与 cunos 现有异常框架的衔接

`#VMEXIT` **不是** CPU 异常，它不经过 IDT。但有两个例外必须处理：

1. **VMRUN 自身失败**（EFER 未开、VMCB 未对齐）会触发真实 `#GP`/`#UD`，走 cunos 的 IDT；
2. **宿主在执行 VMRUN 时被 NMI/SMI 打断**（GIF=0 并不能屏蔽 NMI/SMI 的"进入"，只是延迟其递送）——cunos 无 NMI 源，暂不处理。

因此需要一个"我在 VMRUN 里"的标志位，供 `#GP` 处理器区分"guest 的 `#GP`（应注入）"与"宿主 VMRUN 失败（应报错）"：

```c
/* vmm/vcpu.c */
volatile u32 g_in_vmrun;      /* 1 = 当前位于 VMRUN 与 #VMEXIT 之间 */

static int vcpu_enter_guest(vcpu_t *vc)
{
    g_in_vmrun = 1;
    svm_vmrun(vc->vmcb_pa);   /* 失败则触发宿主 #GP，见 idt 钩子 */
    g_in_vmrun = 0;
    return 0;
}

/* 在 cunos 的 #GP 处理器里（vmm 初始化时挂钩 isr_table[13]）：
 * if (g_in_vmrun) { panic("VMRUN failed: check EFER.SVME / VMCB align / HSAVE"); }
 */
```
